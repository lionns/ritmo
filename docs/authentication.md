# Owner authentication (T-039)

Ritmo requires authentication on Node and Workers. There is no development bypass. Missing or
invalid configuration fails closed with 503. The existing owner is selected by `RITMO_OWNER_ID`;
requests prove that identity, never obtain it from `getOnlyOwner()`. No owner is created by login.

## Configuration and first device

Set these runtime values in your local environment (Node) or ignored `.dev.vars` (local Workers).
Production secret provisioning and deployment remain T-040. Never put values in Wrangler vars or Git.

| Name | Value |
| --- | --- |
| `RITMO_OWNER_ID` | ID of the existing owner row. |
| `RITMO_AUTH_ORIGIN` | Exact public origin, including port when needed; HTTPS, or `http://localhost:PORT` locally. No trailing slash. |
| `RITMO_SESSION_SECRET` | At least 32 random bytes; for example generate 32 bytes and encode as hex. |
| `RITMO_PASSWORD_HASH` | `scrypt-16384-8-5:SALT:HASH`, generated by `hashPassword` below. |

`adapters/http/password.ts` exports `hashPassword(password)` for provisioning. It accepts 15–256
characters, generates a random salt, and uses scrypt N=16384, r=8, p=5 with a 32-byte result. Pass
passwords through protected input, never a command-line argument. For example, pipe a password from
your password manager's secure CLI into:

```sh
node --input-type=module -e 'import { hashPassword } from "./adapters/http/password.ts"; let p=""; for await (const c of process.stdin) p+=c; process.stdout.write(await hashPassword(p.replace(/\r?\n$/, "")));'
```

Store the resulting hash as a secret. It is sensitive even though it is not the original password.
The parameters follow [OWASP's scrypt profiles](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
and fit within Workers memory. [Workers supports node:crypto](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/);
actual workerd password verification is exercised by the HTTP smoke command below.

For an existing installation, use its existing owner ID; do not reset or seed the owner's database.
A fresh empty database needs an owner row prepared locally with an explicit active-cap answer before
login can work. This task does not invent that answer or provide public account creation.

1. Open `/entrar` on the configured origin and sign in with the provisioned password.
2. Open `/ajustes`, name the device and choose “Añadir llave de acceso”. Confirm on the authenticator.
3. On a second device, sign in with the password and repeat. The first credential remains intact.
4. Revoke a named credential in Ajustes. That credential and its existing cookies stop working.
   Synced copies of one passkey share its credential ID, so deleting it revokes all copies.

There is deliberately no unauthenticated “first visitor owns the account” registration, even with
zero credentials. The old T-010 bootstrap plan is replaced by password proof, required by T-039's
wider password/second-device scope. Recovery is direct configuration/database access, not a reset UI.

## Session and ceremony behavior

Cookies are HMAC-SHA256 signed, origin/purpose/owner bound, HttpOnly, Secure, SameSite=Lax, Path=/,
and last 30 minutes without sliding renewal. Rotating `RITMO_SESSION_SECRET` invalidates all cookies
and outstanding signed ceremony tokens. Changing the password hash invalidates password sessions.
Logout clears this browser's cookie; a copied cookie remains usable until expiry or revocation.
Deleting a credential invalidates passkey sessions immediately, because each request checks its row.
No session table exists. `auth_challenges` holds five-minute one-use ceremonies; `auth_attempts`
limits the single owner's authentication operations to ten per minute, atomically across instances.
A sustained attacker can consume that budget; it trades temporary login availability for bounded
password work. Signed-in data access is unaffected. Expired ceremonies are pruned when another begins.

Every mutation requires the exact configured Origin, including login and registration, to prevent
CSRF. Private responses are `no-store`. The middleware guards unknown application routes too;
only `/entrar`, password login, passkey-login begin/finish and public assets bypass the session check.
SSR pages forward the cookie to fixed API paths without following redirects.

Passkeys use ES256 only, required user verification, and `attestation: none`. The server extracts
and validates the COSE EC2 key from authenticator data, rather than trusting a separate browser key.
It checks origin, RP hash, ceremony type/challenge, credential ID, user presence/verification, signature
and counter. Counter-zero authenticators are accepted only while the stored counter is also zero;
once a nonzero counter exists it must increase. One-use challenges prevent replay even with zero
counters. This follows current [WebAuthn verification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion),
which supersedes T-010's assumption that every authenticator increments a counter. No attestation
trust-chain claim is made; unrequested authenticator extensions and unsupported algorithms fail closed.
`getAuthenticatorData()` is required for registration; older browsers retain password access.

The complete SQLite export includes public passkey credentials, ceremony state and rate counters.
It excludes the password hash and signing secret because both live solely in runtime configuration.
An exported database alone therefore cannot restore authentication: reprovision the runtime secrets.
Keep the unencrypted backup private as the UI says; it contains the complete personal record.

## Repeatable verification

```sh
npm run build
node test/manual/auth-http.mjs
RITMO_SQLD_BINARY=/path/to/sqld node test/manual/auth-http.mjs --workers
RITMO_SQLD_BINARY=/path/to/sqld npm run test:integration
```

The smoke commands create disposable databases and loopback servers and clean them up. They test
all routes below against missing, altered and expired cookies, then perform password sign-in,
registration/assertion with an independently signed ES256 fixture, authenticated SSR, export and
immediate revocation. The Worker command runs the actual compiled Worker under workerd with libSQL.
Without sqld the ordinary integration gate explicitly skips the remote suites; that is not remote
verification. Both commands use synthetic credentials, not an actual phone authenticator.
